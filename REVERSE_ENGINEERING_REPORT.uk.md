## A. Загальний діагноз

### Виявлена архітектура
cz-patsum — це посібник реалізації (Implementation Guide, IG) FHIR R4 для tchецького резюме пацієнта (CZ PS / Pacientský souhrn), розроблений Národní centrum elektronického zdravotnictví (NCEZ). Проєкт побудовано на **SUSHI/FSH** (FHIR Shorthand) і публікується за допомогою IG Publisher. Це не виконувальний додаток: немає вихідного коду додатка, бекенду, фронтенду, API або сервісу.

Структура каталогів:
- `input/fsh/profiles/*.fsh` — 26 профілів FHIR (наприклад, CZ_CompositionPS, CZ_BundlePatientSummary, CZ_ConditionPS, CZ_MedicationRequestPS, спостереження вагітності/алкоголю/тутунку/результатів).
- `input/fsh/invariants/*.fsh` — 5 інваріантів FHIR (ips-1, ips-2, bdl-ips-1, hasComponentifValueStringEmpty, hasMemberOrComponent).
- `input/fsh/aliases.fsh` — псевдоніми наборів значень/кодових систем (LOINC, SNOMED, MKn-10, UV-IPS тощо).
- `input/pagecontent/*.md` та `*.xml` — сторінки документації IG (index, principles, design, profiles, knownIssues тощо).
- `input/images/PS-composition.png`, `input/includes/img.html` — графічні ресурси.
- `sushi-config.yaml` — конфігурація SUSHI (id, canonical, залежності, меню, releaseLabel).
- `ig.ini` — конфігурація IG Publisher (вказує на згенерований ресурс `fsh-generated/resources/...`).
- `package-lock.json` — порожній lockfile (тільки `name`, без пакетів).
- `.gitignore` — ігнорує `fsh-generated`, `input-cache`, `output`, `temp`, `template`.

### Технології та залежності
- FHIR R4 (4.0.1)
- SUSHI (FSH)
- HL7 UV-IPS (International Patient Summary) як основа (профіли, набори значень, розширення)
- Залежності IG: `hl7.fhir.uv.ips: current`, `hl7.fhir.us.mcode: current`, `ncez.cz.fhir.core: current`, `ncez.cz.fhir.lab: current` (всі з версією `current`, не закріплені).
- releaseLabel: `ci-build` (правильне написання, не `releaselabel`).

Публічні Issues/PR у цьому знімку не перевірялися.

### Деталі

**REA-001 — Незакріплені залежності (ПІДТВЕРДЖЕНО)**
- Проблема: `sushi-config.yaml` оголошує всі залежності з версією `current` (`hl7.fhir.uv.ips: current`, `hl7.fhir.us.mcode: current`, `ncez.cz.fhir.core: current`, `ncez.cz.fhir.lab: current`).
- Довід: `sushi-config.yaml:33-37`.
- Причина: опція конфігурації, яка не закріплює конкретні версії, підштовхуючи збирання до неконтрольованих змін зверху.
- Наслідок: невідтворювані збирання; ризик пошкодження в результаті несумісних змін у залежностях (lanci постачання).
- Пропонована виправка: замінити `current` на конкретні стабільні версії (або залишити `current` лише якщо це намірно, задокументувавши рішення).

**REA-002 — Відсутність CI/CD та автоматизованих тестів (ПІДТВЕРДЖЕНО)**
- Проблема: немає робочих процесів GitHub Actions, тестів валідації FSH/IG, тестів серіалізації.
- Довід: відсутність директорії `.github/workflows` та файлів тестів у клоні.
- Причина: у IG немає конвеєра неперервної інтеграції.
- Наслідок: зміни у профілях FSH не валідуються автоматично; регресії залишаються непоміченими.
- Пропонована виправка: додати робочий процес CI, який запускає `sushi` (коли доступно) і валідує згенерований IG.

**REA-003 — Порожній/нефункціональний `package-lock.json` (ПІДТВЕРДЖЕНО)**
- Проблема: `package-lock-json` містить лише `"name": "cz-patsum"` та `"packages": {}`, без залежностей.
- Довід: вміст файлу (лише заголовок, без пакетів).
- Причина: lockfile згенеровано без відповідного `package.json` або встановлених залежностей.
- Наслідок: файл без функції; може знувати учасників.
- Пропонована виправка: видалити порожній файл або додати `package.json` з залежностями збирання (наприклад, fhirtypes, sushi), якщо такий намір.

**REA-004 — Розрізнення розділів у режимі `open` (ПІДТВЕРДЖЕНО, вже задокументовано)**
- Проблема: всі правила розрізнення розділів композиції визначені як `open` (наприклад, `section ^slicing.rules = #open`), що дозволяє включення неповідомимих ресурсів.
- Довід: `CzComposition.fsh:57` (`section ^slicing.rules = #open`) та `knownIssues.md` пункт 3 ("All of the slicing rules defined for the section entries have been specified in this version as open...").
- Причина: рішення проектування ради гнучкості за рахунок можливості автоматичної валідації.
- Наслідок: екземпляри можуть містити непотрібні ресурси без відхилення валідаторами.
- Пропонована виправка: переглянути критичні зрізи та розглянути `closed`, де це вимагає безпека клінічна, задокументувавши компроміс.

**REA-005 — Закоментовані зрізи записів (ГІПОТЕЗА)**
- Проблема: різні зрізи записів розділів (медикаменти, алергії, проблеми, процедури тощо) закоментовані у `CzComposition.fsh`.
- Довід: закоментовані рядки (~93-101, 110-118, 126-133 тощо).
- Причина: заплановані зрізи не активовані.
- Наслідок: слабша типізація записів розділів; менш суворе валідування.
- Пропонована виправка: оцінити послідовну активацію закоментованих зрізів з тестами екземплярів.

## C. Повторювані проблеми

Нижче наведено проблеми, які вже визнані супроводжувачами (задокументовано у `input/pagecontent/knownIssues.md`) і все ще присутні в аналізованій версії:

1. **Відсутність представлення діяльності резюме** (хто зробив, що було зроблено (конcilіація медикаментів, алергій тощо), результат, коли і де) — включає елемент "Nature of the IPS" згідно EN 17269 та ISO 27269. Майбутнє: використання ресурсу Provenance.
2. **Специфічність профілів підлежит покращенню** — не всі очікувані правила можуть бути автоматично валідовані через відсутність представлення у зазначених профілях.
3. **Відкрите розрізнення** — всі правила розрізнення записів розділів у цій версії визначені як відкриті. Це зроблено для гнуckoсті IPS за рахунок можливості повної автоматичної валідації екземплярів. Технічно профіль може дозволяти включення непотрібних ресурсів. Специфікаторам рекомендується додавати додаткові обмеження або зрізи для зменшення цього ризику. Майбутні версії можуть переглянути поточний вибір.
4. **Більш обмежені словники** — вибір у цій версії відображає потребу балансувати між зменшенням опціональності для покращення взаємодії та уникнення занадто суворих обмежень для спрощення локального впровадження. Визнано поточний відсутність у деяких випадках всебічно визнаних і вільно використовуваних словників (наприклад, для ідентифікації медикаментів) та потребу розширювати набори значень на основі нового вмісту SNOMED CT та SNOMED IPS Terminology. З цієї причини зв'язок обов'язковий лише у кількох випадках; використано передбачені або розширювані зв'язки.
5. **Синергія з International Patient Access IG** і впровадження Provenance (майбутній розвиток).

Джерело: `input/pagecontent/knownIssues.md` (пункти 1-5 та Future Development).

**Результат: заходів не виявлено статичним аналізом, що було проведено.**
